# 実装の構造を見直す

実装が終わった後に、ユーザーが `/structure` と入力したときに使う。
目的は、コードをなるべく綺麗・シンプル・エレガントな状態に保つこと。細かいコードの書き方よりも、
歪な構造になっていないかを重点的に見る。特に、正しい責務の分担になっているかを重視する。

以下の 4 つの観点を 4 人のレビュー用 subagent たちにそれぞれ依頼し、それらをまとめて一本のレポートにする。
レポートの形式は、1, 2, 3, 4, 総評の形。
subagent が使えない環境の場合は、それぞれをできる限り独立にレビューする。
yuru の新規 session は作成しなくて良い。

レビュー対象は unstaged があれば unstaged、unstaged がなく staged があれば staged、staged がない場合はそのブランチでコミットされたもの。
会話の文脈からしてこの基準から外れる場合や、明確でない場合はユーザーに確認すること。

## 1. 行数の増減を調べる

- テストとドキュメント以外の行数増減を調べる。
- 行数が膨らんでいるところは妥当な増え方か説明する。
- 不要な複雑さや無駄な処理で行数が増えているところを探し、もしあれば改善案を提示する。

コードゴルフが目的ではない。行数を削るために設計を壊したら本末転倒である。行数はあくまでコードの
嫌な匂いを嗅ぎ取るきっかけであって、目的はコードを綺麗に保つことである。

## 2. 命名と実装が一致しているか調べる

- 宣言されている名前（ディレクトリ名、ファイル名、関数名）とその中身の実装が一致しているか
- 既存の実装が都合よく使えるからといって、名前と違うことを追加でやらせていないか
- 抽象的すぎる名前がついていないか

正確な名前をつけることだけが目的ではない。
上手く名前をつけるのが困難な時は、責務のはっきりしない実装の塊を無理やりまとめているのが原因の場合があり、
これは名前を工夫するのではなく責務の分割を考え直さなければいけない。

## 3. ドメイン知識が凝集されているか調べる

- 複雑なロジックはそのドメインを扱うモジュールに閉じられているか
- provider 固有の知識やロジックが外に漏れ出ていないか
- Git や GitHub の詳細な処理が main/git や main/github に凝集されているか
- 汎用的なロジックを扱う層にアプリケーション固有の事情が書かれていないか

## 4. 既存コードが原因で複雑になっていないか調べる

- 互換性を神経質に考えすぎて複雑になっていないか（現時点でユーザーは１人なので互換性は考える必要がない）
- 既存の慣習に従うことで複雑になっていないか

既存の設計を変えることに対して神経質に考える必要はない。ゼロベースで理想の設計を考えること。
ただし、根本修正が大掛かりで一緒に直せない場合は別途バックログに積むことを考える。
