# F60 / F61 / F66: 並び替えの UI 設計

Last updated: 2026-08-18

## この doc の範囲

repo / worktree / primary session の 3 つを drag & drop で並び替える、その**見え方と操作**を決める。
並び順をどこに持ち、どう永続化し、どの IPC で渡すかは
[F60-F61-F66-order-design.md](F60-F61-F66-order-design.md) (構造設計) が扱う。
2 つの doc の噛み合わせは最後の「構造側との境界」にまとめた。

モックアップ: [../mockups/F60-F61-F66-reorder.html](../mockups/F60-F61-F66-reorder.html)

## 何を並び替えるのか

| 対象 | 場所 | 掴む単位 | 動かないもの |
| --- | --- | --- | --- |
| repo (F61) | サイドバーの repo 一覧 (`.repo-list`) | repo group (ヘッダ行 + 配下の worktree カード) | — |
| worktree (F66) | repo group の中 (`.repo-task-worktrees`) | task worktree のカード | main worktree のカード (常に先頭) |
| primary session (F60) | Terminal ホームの Sessions セクション / セッションタブ | session の行 / タブ | Suggested と New session の行、Home タブ、primary でない runtime のタブ |

3 つとも**1 つの入れ物の中の 1 次元の並び替え**に閉じる。repo をまたいで worktree を動かすことも、
worktree をまたいで session を動かすこともできない。どちらも Git や metadata 上の所属が変わる操作で、
並び替えとは別物だから。入れ物をまたがないので drop 先の判定は「この入れ物の中の何番目か」だけで済み、
これが以下の設計を単純にしている前提になっている。

新規追加は従来どおり末尾 (worktree も session も)。並び替えても新規の入る場所は変わらない。

## 3 か所で共通のインタラクション

### 掴む — 専用のハンドルを作らず、項目そのものを押して動かす

- 項目の上で pointerdown し、**4px 動いたら並び替えを開始する**。4px 動く前に pointerup したら
  今までどおりのクリック (worktree の選択、session の表示)。
- 項目の中の副操作ボタン (worktree カードの ︙、タブの ×、repo 行の +、session 行の Detach) の上での
  pointerdown では始めない。
- **並び替えは選択を変えない。** タブを動かしても表示中のタブは変わらないし、カードを動かしても
  選択中の worktree は変わらない。
- カーソルは掴んでいる間だけ `grabbing`。掴む前に `grab` へ変えることはしない。常時「掴めそう」に
  見せると、クリックで選ぶという主用途がぼやける。

代替案として、ホバーで出るグリップ (⋮⋮) を項目の左端に置く形も考えたが採らない。発見しやすくなる
代わりに 3 か所すべてで左側に固定の余白が要る。worktree カードは既に右上のホバーで ︙ が出るので、
左右に隠れボタンが並ぶことになる。

### 動かす — 隣の項目がその場でどく

- 掴んだ項目はポインタに 1:1 で追従する。**ドラッグ軸だけ**動かし、直交方向 (縦のリストなら横) の
  動きは無視する。
- ほかの項目は落ちる場所を空けて 1 スロット分ずれる。ずれる側は `transform 140ms ease` で滑らせ、
  掴んだ側は transition を持たない (ポインタから遅れないように)。
- 掴んだ項目は細い枠と影で浮かせる (`box-shadow: 0 0 0 1px var(--border-strong), 0 14px 28px rgba(0, 0, 0, 0.55)`,
  `opacity: 0.95`、`z-index` を 1 段上げる)。枠がないと、隣の項目と地続きに見えて浮いていることが読めない。
  元の場所に点線などの placeholder は描かない。ずれた隣人が作る空きスロットが
  そのまま「落ちる場所」で、ポインタがそこにあるときは空きが掴んだ項目自身に隠れる。
- 掴んだ項目は自分の入れ物の中にクランプする。repo group の外や Sessions セクションの外へは
  視覚的にも出られない。「ここから出られない」が触って分かる。

挿入線 (2px の線) だけを出して他は動かさない方式も考えたが、落ちた後の並びを頭の中で組み立てる必要があり、
カードのように高さのある項目では読み取りづらい。実物が動くほうを採る。

### 落とす / やめる

- pointerup で確定。並びが変わっていなければ何も書かない。
- **Esc と pointercancel で取り消す。** 元の並びに戻して、何も書かない。

### 画面外にはみ出す場合 — 端に近づいたら自動スクロール

スクロールする入れ物は `.repo-list` (サイドバー) と `.terminal-session-start` (ホーム) の 2 つだけ。

- スクロールコンテナの上端・下端から **28px** を反応域とし、端に近いほど速く (端で最大 14px/frame)
  スクロールする。
- ポインタを止めたままでもスクロールし続けるので、**位置の再計算は pointermove ではなく
  rAF ループの中で毎フレーム行う**。
- 掴んだ項目がその方向の端 (先頭 / 末尾) に達したら自動スクロールを止める。行き止まりなのに
  スクロールだけ進む、を防ぐ。

セッションタブは横に長くなるが、**タブ列はスクロールしない**。タブが増えたときは横スクロールせず
タブ自体が縮む (I21 の固定仕様)。つまりタブは常に全部見えているので、タブの並び替えに
自動スクロールは要らない。

### 座標の持ち方 — 自動スクロールと両立させる要点

- drag 開始時に各項目の矩形を**1 回だけ**測る。ドラッグ中はメンバーと並びを固定する (後述) ので
  測り直さない。
- ただし viewport 座標で持つとスクロールした瞬間に無効になる。**スクロールコンテナの content 座標**
  (`rect.top - containerRect.top + container.scrollTop`) で持ち、ポインタも同じ座標系に変換する。
  こうすると自動スクロールしても再測定が要らず、rAF ループの中は純粋な計算だけになる。

### 落ちる位置の決め方 (ライブラリなしで書ける計算)

`H` = 掴んだ項目の外寸 (高さ + gap。横並びなら幅 + gap)。

1. 「掴んだ項目を抜いた後」の各項目の中心を求める。index が掴んだ項目より前ならそのまま、
   後ろなら `-H`。
2. 挿入 index = その中心が掴んだ項目の中心より手前にある項目の数。
3. 表示は、index が移動元と挿入先の間にある項目を `±H` だけ transform でずらす。

2 の式は「抜いた後の並び」という動かない基準に対する単調な比較なので、境界で行ったり来たりする
ちらつきが起きない (挿入先に応じて基準側も動く方式だと不動点の問題が出る)。

3 の「ずれる量はどれも `H`」は項目の高さがバラバラでも成り立つ。1 つ抜いて 1 つ入れるだけなので、
間にある項目はどれもちょうど `H` だけずれる。worktree カードの 62px (primary あり) と 52px
(primary なし) の混在も、ラベル長で変わるタブの幅も、この式のままでよい。

横方向 (タブ) は y を x に読み替えるだけで同じ。**3 か所ともこの計算で足りるので、並び替えの
ライブラリは入れない。**

## 場所ごとの見え方

### repo (F61)

- 掴むのは repo のヘッダ行 (`.repo-row`)。動くのは**repo group 全体** (ヘッダ + 配下の worktree カード)。
- 掴んでいる間、配下のカードは `opacity: 0.35` に落とす。動いているのはヘッダだと読めるようになり、
  worktree を 10 個持つ repo でも塊が重く見えない。
- `.repo-group` は今は背景を持たずサイドバーの地の色が透けている。掴んでいる間だけサイドバーより
  明るい地 (`#1d2532`) と角丸を与えて、下の group から浮かせる。

代替案として、ドラッグ中だけ全 group をヘッダだけに畳む形も考えたが採らない。repo が多いときに移動が
楽になる代わり、drag 開始の瞬間にレイアウトが変わって掴んだ行がポインタから逃げる
(scrollTop の補正が要る)。

### worktree (F66)

- 掴むのは task worktree のカード。main worktree のカードは掴めず、drop 先にもならない。
- クランプ範囲はその repo の task worktree 領域。上は main worktree カードの下端、下は group の下端。
  ほかの repo の領域には視覚的にも入れない。
- ドラッグ中はホバーで出る ︙ を隠す。

### primary session (F60) — ホーム

- 並び替えられるのは Sessions セクションの行だけ。Suggested と New session のセクションは掴めず、
  drop 先にもならない。クランプ範囲は Sessions セクションの矩形。
- inactive の行 (`opacity: 0.72`) もそのまま掴める。並び替えに runtime の有無は関係しない。

### primary session (F60) — タブ

タブの並びは今も独自の state を持たず、`primarySessions` の順をそのまま投影している (`TerminalTabs`)。
**この投影関係を壊さない**のが方針。詳細は次節。

- 掴めるのは primary session のタブだけ。Home タブと、primary でない runtime のタブ
  (standalone terminal など、今も primary タブの後ろにまとめて並ぶ) は掴めず、drop 先にもならない。
  クランプ範囲は primary タブの並びの範囲。
- タブは背景が半透明なので、掴んでいる間だけ不透明な背景 (`--bg-panel`) と `--border-strong` の枠を
  与える。

## タブでの並び替えと inactive session

**問題。** タブは live runtime の投影なので、runtime を持たない inactive session はタブに出ない。
一方で並び順は inactive も含む primary session 全体の 1 本の並びである。タブの上でドラッグしても、
見えていない inactive をどこに置くかがそのままでは決まらない。

**採る案: タブの D&D は、ホームと同じ 1 本の並びに対するショートカットとして扱う。**
タブ列に独自の並びは持たせない。ドラッグの結果は次の 1 行の規則で全体の並びに翻訳する。

> 落とした場所の**左隣のタブ**を目印にして、全体の並びでもそのタブの直後へ移す。
> 左端 (先頭のタブより左) に落としたときは左隣がいないので、全体の先頭に仮想の左隣が
> あると考えて**全体の先頭**へ移す。

目印は常に「左隣の見えているタブ」なので、目印が inactive にずれることがない。

例。全体が `A(active) B(inactive) C(active) D(inactive) E(active)`、タブ列は `A C E`。

- E を先頭に落とす → 全体は `E A B C D`、タブ列は `E A C`。
- A を C と E の間に落とす → 全体は `B C A D E`、タブ列は `C A E`。
  B 自身は動いていない。前にいた A が抜けたので先頭になっただけ。

この規則だと、**タブ列で見える active 同士の相対順は必ずドラッグしたとおりになり**、動かした 1 件を
除いて inactive の相対順も変わらない。タブ列が嘘の並びを見せることはない。

この規則では、タブ 1 スロット分の移動でもホーム側では複数行分動いて見えることがある。
着地点は新しい左隣タブの直後なので、その間に挟まっていた inactive の行はすべて越える。
目印を見えているタブに固定する以上これは避けられない (「1 スロット = 全体の並びで 1 つ分」に
すると、間に inactive があるときタブが視覚的に動かなくなる)。

先頭に inactive がいる場合、左端に落とすとその inactive より前 (全体の先頭) に来る。
「端に落としたのに見えない要素がじゃまをして端に届かない」ことは左端では起きない。
一方で右端は「最後のタブの直後」なので、末尾に inactive がいると**一覧全体の末尾には届かない**。
この左右の非対称は「張り付く目印が左隣」という 1 つの規則から自然に出るもので、
右を仮想の目印で特別扱いしないのは「タブだけを見て操作している人にとっての末尾は
見えているタブの末尾」という考え方による。

**採らなかった案。**

- **ドラッグ中だけ inactive を仮のタブとして差し込む。** タブ = live runtime という固定仕様が崩れる。
  ドラッグを始めた瞬間にタブの本数と幅が変わって掴んだタブがポインタから逃げる。落とした後に消える
  タブへ向かって落とす操作は理解しづらい。
- **タブは並び替えない (ホームだけにする)。** 3 か所の体験を揃える要求を満たさない。タブが並びの
  投影である以上「タブを動かせば並びが変わる」という期待のほうが自然。
- **タブに独自の並びを持たせる。** 並び順の source of truth が 2 つになる。
- **inactive を「直前の active にくっついた塊」として一緒に動かす。** タブ列での結果は上の規則と
  同じになるが、ホーム側では見えない塊の概念に従って複数行が動く。説明できない動きになる。

## 並び替えが副作用として変えるもの

**サイドバーのカードが代表として出す session が変わる。** カードは先頭 primary を固定で出す (I21)。
primary session の並び替えは、この代表を選ぶ操作でもある。隠れた副作用というより「カードにどの
セッションを出すか」を選べるようになるという良い面があるが、驚きにしないために書いておく。

worktree を選び直したときに開くのは常にホームなので、並び替えが「最初に開くセッション」を
変えることはない。

## ドラッグ中に一覧が更新されたら

`repos` は preview・activity・PR 監視から頻繁に push される。ドラッグ中に配列が差し替わると、
開始時に測った矩形が意味を失う。失敗時の挙動なので明示的に決めておく。

- **ドラッグ中は「並び (ID の列) とメンバー」だけを開始時のスナップショットに固定する。**
  中身 (preview の文字、activity のドット) の更新はそのまま通す。行の高さは 1 行省略で固定なので、
  中身が変わっても矩形は変わらない。ドットが数秒止まって見える副作用も避けられる。
- **項目が増減したらドラッグを取り消す** (worktree の削除、session の detach、repo の追加、
  新しい worktree の出現)。矩形と実物が食い違ったまま落とすほうが危ない。取り消しは黙って元の並びに
  戻すだけで、何も書かない。「続行して drop 時に検証する」形も考えたが、ドラッグ中ずっと
  「見えている位置」と「落ちる位置」がずれ続けるので採らない。

## キーボードでの並び替えは作らない

Alt+↑/↓ で 1 つずつ動かす操作は入れない。並び替えは D&D だけで行う。

- 既存の操作は変えない。worktree カードの Enter / Space は今までどおり選択で、「Space で掴んで
  矢印で動かして Space で置く」方式にもしない。
- 3 か所とも要素は既にフォーカス可能 (カードは `role="button"` + `tabIndex=0`、ホームの行とタブは
  button) で、並び替えのためにフォーカス構造や tab order を変えるところは無い。
  つまりキーボードだけで使う人にとって、この機能が入っても今より不便になるところは無い
  (並び替えができないだけで、選択と表示は従来どおり)。

## F67 (ファイルをターミナルにドロップ) との関係

F67 は**転送**のドラッグ (項目を別の面へ運ぶ)、F60/F61/F66 は**並び替え**のドラッグ
(項目を同じ列の別の位置へ動かす)。掴む対象が重ならない (ファイルツリー / Changes の行 と
repo / worktree / session の項目) ので、同じ要素が両方の意味を持つことはない。

揃えたいところ:

- 掴んだものが浮く見た目 (影と opacity)、4px の閾値、副操作ボタンの上では始めない規則。
  ユーザーから見ると「掴んで運ぶ」は同じ操作なので、ここが違うと不揃いに感じる。
- ドラッグ中に preview の iframe や xterm がポインタを奪わないようにする土台。1 つにしておきたい。

分けたいところ:

- **落とせる場所の示し方。** 並び替えは「隣がどく」で示す。転送は「落とせる面が縁で光る」で示す。
  この 2 つを混ぜない (並び替えでターミナルが光る、転送で隣がどく、はどちらも嘘になる)。
- **実装機構は別でよい。** HTML5 の drag & drop (dataTransfer) は転送向きで、Finder からの
  ドロップと同じ経路にできる利点がある。並び替えには向かない (ゴースト画像とアニメーションを
  制御できず、live reflow が作れない)。見た目だけ揃えて、機構は用途ごとに選ぶ。

## 実装メモ (renderer 側)

- 3 か所で同じ計算をするので、pointerdown → 閾値 → rAF ループ → drop / cancel までを 1 つの hook に
  まとめる。既存のポインタドラッグ基盤 `runPointerDrag` (`utils/layout.ts`) は pane のリサイズ用で、
  Esc の取り消しも rAF ループも自動スクロールも持たないため、そのままの流用はできない。
  並び替え用はその隣に別ファイルで置く。
- ドラッグ中に持つ state は「掴んだ項目の ID」「ポインタの移動量」「現在の挿入 index」だけ。
  並び自体は props (repos / worktree) のまま持ち、state に複製しない。
- ドラッグ中は preview の iframe がポインタを奪う (`runPointerDrag` のコメントにあるとおり)。
  `runPointerDrag` と同じく body に class を付けて iframe の当たり判定を切る。pointer capture でも
  同じことができるはずだが、preview iframe で実際に確かめてから採用する。
- 新しい CSS は「掴んでいる項目」「ずれる項目」の 2 クラスと、場所ごとの微調整だけ。
  モックアップの `.reorder-dragging` / `.reorder-shift` がそれ。

## 構造側 (データモデル・永続化) との境界

構造設計 doc の決定に対して、UI 側の答えと確認事項。

1. **送るのは「並び替え後の全 ID 配列」で問題ない。** 構造側は
   `repos:reorder` / `worktrees:reorder` / `worktreeSession:reorderPrimary` の 3 つで、
   いずれも全要素の ID 配列を受け取り、ID セットが現在の対象と一致しなければ書き込まずに error を
   返す。UI 側は**ドラッグ中に項目が増減したらドラッグを取り消す**ので、この不一致は
   「drop してから main が処理するまでの隙に、別インスタンスやエージェントが worktree を作った」
   ような稀なケースにだけ起きる。
2. **楽観更新はしないが、並びは往復させない。** 構造側の書き込みは同期で軽いので、UI は invoke の
   結果を待つ。待っている間は**ドラッグ終了時の並びを描き続ける** (props の古い並びに一度戻して
   から新しい並びに切り替える、をしない)。
3. **error が返ったときの UI の動きは原因で分岐しない。** ID セット不一致でも書き込み失敗でも、
   保持していた並びを捨てて一覧を取り直すだけ。トーストは出さない。

   セット不一致は「drop してから main が処理するまでの数 ms に、別インスタンスやエージェントが
   worktree を作った」という並行操作の結果で、データは壊れておらず、もう一度ドラッグすれば済む。
   楽観的な書き込みが拒否されただけなので**正常系として扱う**。ユーザーへのフィードバックは
   「並びが元のまま戻り、一覧に新しい worktree が現れる」で既に出ている。

   握りつぶしにはならない。並び替えの書き込み失敗は main 側が既存方針どおり `recordAppError` で
   error center (サイドバー下部の Errors 行) に残す (構造側 doc の「失敗時の挙動」)。
   UI 側から追加でお願いすることは無い。

   **送る前**の取り消し (ドラッグ中に項目が増減したとき) も同じく黙って元の並びに戻すだけなので、
   送る前と後でユーザーに見える動きは変わらない。

   代替案: 書き込み失敗だけトーストで知らせる (resume 失敗と同じ `onError` の経路)。
   そのためには renderer が 2 つの原因を区別できる必要があり、`Result` の error に種別を持たせる
   依頼が構造側に増える。並び替えの書き込みは metadata の同期書き込み 1 回で、失敗はディスク側の
   異常に限られるため、その依頼に見合うかは要判断。
4. **main worktree は常に先頭固定でよい** (構造側の「要確認」への答え)。掴めず、drop 先にもならない。
   `worktreeOrder` が task worktree だけを対象にするのと一致する。
5. **タブ順は metadata の primary session 順に自動で追随する** ので、タブのための順序は要らない。
   タブでのドラッグも「タブでの並び替えと inactive session」の規則で全 ID 配列に翻訳してから、
   ホームと同じ `worktreeSession:reorderPrimary` に送る。

## 分かれ目だった 5 点の決定 (2026-08-18)

上の各節に反映済み。論点として何を比べたかだけ残す。

1. **掴み方** → 項目全体を押して動かす。ホバーで出るグリップは、3 か所すべてで左に固定の余白が要る
   のと、カードの左右に隠れボタンが並ぶのを避けて採らない。
2. **repo のドラッグ** → group ごと動かして中身を減光する。ドラッグ中だけヘッダに畳む案は、開始の
   瞬間にレイアウトが変わって掴んだ行がポインタから逃げるので採らない。
3. **タブの D&D → 全体の並びへの翻訳規則** → 「左隣のタブの直後」の 1 原則に統一。
   左端は仮想の左隣の直後 = 全体の先頭 (先頭に inactive がいても越えられる)。
   右端は最後のタブの直後で、一覧全体の末尾にはしない (末尾に inactive がいると届かない)。
   当初の文面は左端を「先頭のタブの直前」としていて、先頭に inactive がいる場合に
   「端に落としたのに端に届かない」読みが可能だったため明確化した。
4. **キーボードでの並び替え** → 作らない。並び替えは D&D だけ。
5. **ドラッグ中に項目が増減したとき** → ドラッグを取り消す。続行して drop 時に検証する案は、
   ドラッグ中ずっと「見えている位置」と「落ちる位置」がずれ続けるので採らない。
