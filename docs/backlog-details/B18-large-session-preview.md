# B18 巨大なセッションログの preview 取得を高速化する

Last updated: 2026-08-26

## 問題

Codex セッションの preview に必要なのは末尾側の assistant message だが、取得時には rollout の
全履歴を先頭から走査している。ファイルを streaming で読めば巨大な文字列の生成によるクラッシュは
避けられるが、必要な message が見つかるまでに全履歴を読む時間は短くならない。

preview の取得では、rollout 全体を走査せず、末尾側から必要な assistant message を見つけられる
ようにする。

## 具体例

2026-08-24 に作成され、2026-08-26 まで使われた Codex セッションで次を観測した。

- rollout は 765MB、2965 行で、1 行あたり平均約 258KB
- streaming 読み込みに変更した試作ではクラッシュしなくなったが、preview の取得に約 35 秒かかった
- ファイルの約 94% は画像生成結果の base64 で、同じ画像が異なるイベントに重複して記録されていた
- 画像は別ファイルにも保存済みだったが、preview と無関係な base64 を含む全イベントを走査していた

35 秒という値や画像生成結果の比率はこのセッション固有の具体例であり、対応の対象は
「preview の取得にログ全体の走査が必要」という構造そのもの。
