P29 + P30 — 右ペインのタブ

P29（ブックマーク数をタブに表示）と P30（右ペインの幅を縮めても崩れないようにする）は、 同じ 1 本のタブ列の話なので合わせて考える。P29 でバッジがもう 1 つ増えるぶん、 タブ列はいまより約 24px 広くなり、幅の問題が一段きつくなる。 右ペインはドラッグで 220px まで縮められる（usePaneLayout の下限）ので、 220px で成立することを設計の目標にする。

1. いまの壊れ方現状

下は いまの CSS のまま、パネルの幅だけを変えたもの。 ラベル付きのタブ 4 つにはパネル幅 340px 要る（タブ列そのものが 308px + 左右 16px）ので、 既定の 375px から少し縮めただけで足りなくなる。 P29 で Bookmarks のバッジが増えると、これが 368px まで上がり、 既定の 375px に 7px しか余らなくなる。 .tab-select は flex: 1; min-width: 0 なので、足りなくなるとピルのほうが先に縮み、 文字がピルからはみ出して隣と重なる。Files タブの操作ボタンは flex-shrink: 0 なので、 縮まずにパネルの外へ押し出されて消える。

2. P29 — Bookmarks にカウントを出す提案

見た目は Changes のカウント（.panel-tab-count）をそのまま使う。新しい書き方は足さない。 0 件のときはバッジごと出さない——ここは Changes のいまの挙動も変える（現状は 0 を出している）。 バッジは「向けるべき量がある」という合図で、0 はその合図を出さないために場所を取っている状態になる。 機能ごとの分岐ではなく、カウント 1 本の規則を変えるだけ。

375px — 件数がある

375px — 両方 0 件

差分もブックマークも無いときは、タブが 4 つ並んでいるだけになる。 「0 件であること」はバッジが無いことで伝わる。

220px — 件数がある（192px）

220px — 両方 0 件（140px）

畳んだときにバッジ 1 つが約 24px を占めるので、0 で消す規則は狭いときの余裕にも効く。

ちらつきも消える：Changes のカウントは gitPathStates から出ていて、 これは最初の polling が返るまで空。いまはマウント直後に一瞬 0 が出てから実数に変わる。 0 で消す規則なら、この一瞬の 0 も出なくなる。

数の出どころ：いまブックマークの取得と購読は BookmarksPane の中にある。 タブにも数が要るので、取得と購読を ExplorerPanel に上げて、 一覧は props で BookmarksPane に渡す。 Changes のカウントが gitPathStates から出ているのと同じ形になり、 情報源は 1 つのまま（表示専用の件数を別に持たない）。 追加・削除・リネームの IPC 呼び出しは BookmarksPane に残す。

3. P30 — 幅で「ラベルを畳む」提案

タブを 4 つとも残したまま 220px に収める方法は、実質ラベルをアイコンに替えるしかない （ラベル付きのタブ列は詰めても 314px までしか縮まない。アイコンなら 192px、カウントが両方 0 なら 140px）。 あわせて、このタブ列だけ間を 6px → 4px、ピルの内側を 10px → 8px に詰める。 P29 のバッジぶんで既定の 375px がほぼ埋まってしまうのを戻すためで、幅に関わらず効かせる （.tab は session のタブ列とも共有しているので .panel-tabs の中だけに限る）。 切り替えの境界は 366px（次の §4 参照）。 切り替えの判断は CSS の container query で行う：.changes-panel を container-type: inline-size にすると、パネル自身の幅で中の表示を切り替えられる。 幅を JS で測って props で配って回る必要がなく、再描画も起きない。

仕組みは ユーティリティ 2 つだけ：.panel-wide-only（狭いと消える）と .panel-narrow-only（狭いときだけ出る）。 タブのラベル／アイコンも、Files の操作ボタンのラベル／アイコンも、同じ 2 つで説明できる。 タブ側の title / aria-label は幅に関わらず常に付けるので、 アイコンだけになっても読み上げとツールチップは変わらない（Tab の label は既にある）。

4. カウントの桁数と、切り替えが起きる幅

バッジの幅は桁数で変わるので、ラベル付きのタブ列に必要なパネル幅も件数で動く。 下は詰めたあとの実測値（単位 px）＝ ラベルを出したままにできる最小のパネル幅。 既定の 375px では、4 桁どうし以外はすべてラベルのままで、リサイズしない限りアイコンにはならない。

境界は固定値しか置けないので、現実的に起きうる最大に合わせて 366px にする。 ラベルが出るのは 367px 以上なので、必要幅が 367px 以下の組み合わせは、どの幅でも溢れない （表の まで）。大きな変更中に起きる Changes 4 桁 / Bookmarks 1 桁は 360px で、ここに 7px 収まっている。

残る の 3 つは、片方が 4 桁で、もう片方も 3 桁以上という組み合わせ （変更 1000 ファイル超 かつ ブックマーク 100 件超）。溢れるのは 367〜370px のような数 px 幅の帯だけで、 そこでも文字がピルから少しはみ出す程度。 ここまで境界を上げると既定の 375px との差が無くなるので、合わせないことを選ぶ。

副作用：境界が 366px なので、既定の 375px から 10px ほど縮めるとアイコンに切り替わる。 ここを厚くしたいなら、右ペインの初期幅（usePaneLayout の useState(375)）を 400px にすると 34px の余裕になり、4 桁どうしも収まる。ただし端末側が 25px 狭くなる。

6. 検討した代替案

案 B — 選択中のタブだけラベルを残す

中間段階をもう 1 つ作る案（366px 以上は全ラベル / 250〜366px は選択中だけ / それ未満は全アイコン）。 既定の 375px から 10px ほど縮めるだけでアイコンだけになるのが気になるなら、container query を 1 つ足すだけで作れる。 採らなかった理由：220px で成立させるという要件は案 A で満たせる。段階が増えるぶん、 ドラッグ中に見た目が 2 回変わる。まず案 A を入れて、実際に縮めて使ってみて足りなければ足す。

案 C — タブ列を横スクロールさせる

CSS 3 行で済み、ラベルも消えない。 採らなかった理由：タブが 4 つしか無いのに、見えていないタブがある状態が常態になる。 P29 のカウントも、スクロールしないと見えないなら「一目で把握したい」が満たせない。

案 D — 幅を JS で測って分岐する

ExplorerPanel には既に useElementSize があるので、 panelSize.width で分岐することはできる。 採らなかった理由：幅が変わるたびに React の再描画が走る。 いま P22（再描画の波及を減らす）を控えていることもあり、 見た目だけの分岐を state に持ち込む理由が無い。CSS で足りる。

7. 変更点まとめ

P29

  • ExplorerPanel がブックマークの取得と購読を持ち、一覧を BookmarksPane に props で渡す。
  • Bookmarks タブに .panel-tab-count を足す（Changes と同じ見た目）。
  • カウントは 0 件のとき出さない。Changes の現状（常に 0 を出す）もこれに合わせる。

P30

  • .changes-panel を container-type: inline-size にする。
  • .panel-tabs の gap を 4px、その中の .tab-select の内側を 8px に詰める（幅に関わらず）。
  • .panel-wide-only / .panel-narrow-only の 2 つと、@container (max-width: 366px) の 1 ブロックを足す（ブロックの中で左右の余白も詰める）。
  • 4 つのタブにアイコンを足す（FileDiff / Folder / Search / Bookmark）。Tab の label は 4 つとも常に渡す。
  • Files の Changed dirs / Collapse all にもアイコンを足し、ラベルを畳めるようにする。Files ラベルは狭いときに落とす。
  • 幅と無関係な直し：.change-section-base（ブランチ名）に省略指定を入れ、セクション名を flex-shrink: 0 にする。

Tab と Button の中身には手を入れない。どちらも「中身は呼び出し側が決める」作りなので、 アイコンとラベルを並べて渡すだけで済む。
